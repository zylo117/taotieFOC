# 里程碑与对照基线

## 里程碑 2026-11-17-A：内部规划运动默认改走窗口 DMA 引擎（多走问题阶段性修复）

**标签：`milestone-window-engine`（提交 `7c4271f`）。以后判断"是不是新引入了每趟多走"，
一律用本文件的判据和数字做对照。**

### 症状（用户报告，长期存在）
每次定步数运动都固定"多走" 0.1~0.3°，单趟看着时大时小，连续多趟肉眼可见越跑越偏。
用户自己 git 回滚 bisect 出的分界：`c756ffa` 干净、`3181616`（"unify pulse output engine:
all internal motion goes continuous PWM"）起变差。

### 决定性判据（这就是以后要复用的对照实验）
脚本 `scripts/tt_drift_tmp.py`：**连续 20 趟同向定步数运动，累计编码器位移 − N×命令**。
单趟读数噪声 ±3 微步（±0.17°）会把每趟的小偏差盖住；20 趟累积把分辨率提高到
**约 ±0.1 微步/趟**，这才第一次把"每趟固定多走约一个微步"暴露出来。

```
python scripts/tt_drift_tmp.py 3200 20      # 开环，60/1200/6000
python scripts/tt_drift_tmp.py 6400 10
```

| 版本 / 出口 | 3200×20 累计 | 6400×10 累计 | 每趟 |
|---|---|---|---|
| `c756ffa`（窗口 DMA） | **+1.44 微步** | — | +0.07 |
| HEAD 连续 PWM（`0x187=0`） | **+18.08 微步（+1.02°）** | +11.50 微步 | **+0.90** |
| **本里程碑 窗口 DMA（`0x187=2`，现为默认）** | **+0.25 微步（+0.014°）** | **−0.20 微步** | **≈ 0** |

**验收线：3200×20 累计误差绝对值 ≤ 2 微步（≤0.11°）。超过即视为回归。**

### 根因（一条构造性事实 + 一条待证推断）
- **已证实**：`0x134` 账本峰值恒等于命令步数 ⇒ 软件要的步数没错；同一版固件只切换出口
  （`0x187` 一个 bit）就从 +18 微步变 +0.25 微步 ⇒ **多走发生在物理输出级**，不在账本、
  不在 PID/补偿、不在 SETTLE。
- **窗口路径为什么不可能多发**：`StepOutputChannel::emit` 里 `seq_count = num_steps + 2`，
  头尾 guard 的周期值只有 1 与 5 个 tick，而 CCR = 250 tick（1 µs）——计数器走不到 CCR，
  guard 不产生上升沿；中间 N 格每格恰好越过 CCR 一次。**"发几个沿"由序列长度决定，
  与账本由构造一一对应。**
- **连续 PWM 为什么会多**：步数是 `速率 × dt` 的时间积分，结束用 `CEN=0` 砍掉在飞周期，
  **它从不数自己发了几个沿**；装载那一下（`stepper_init_motion_timer`：CEN 关→钉低→
  `tmr_base_init(TMR2,1,psc)` 内含 `ovfswtr` 立即更新事件→配 CH3/CCR→DIR→CNT=0→MOE→CEN）
  可能先产出一个"驱动器会计数、而账本要等下一个 50µs 控制拍才开始记"的沿，收尾那一刀
  又未必砍掉同一个 ⇒ 每趟净差约 +1 个沿 = +0.9 微步，与实测 +0.90 微步/趟吻合。
  **这一条尚未被仪器单独抓到**（改引脚高阻/常开 MOE 无效，说明不是悬空耦合，而是沿被
  合法多产出一次；`e8186b8` 加 CCR 预装载后偏置从 2.4 降到 1.1，也指向边界沿的产出）。
  钉死办法：把 STEP 接进另一个定时器做输入捕获计数，或用 TMR3 数 TMR2 溢出，与命令沿数
  直接对比，20 趟即可判定。

### 默认与代价（不要搞错）
- 默认 `engine_tuning_ = 0x0002`（`closed_loop_controller.h:557`）：内部规划运动走窗口 DMA。
- **写 `0x187=0` 切回连续 PWM**：拿回 1.5Mpps 全速域，但同时拿回"每趟 +1 微步"的老毛病，
  高速工况用它之前先跑一次 `tt_drift_tmp.py` 对照。
- 窗口引擎上限 **440 kpps ≈ 4125 RPM@32µs**（`startMotion` 已按
  `StepOutputChannel::windowCapacity(50µs)` 重钳量程）；撞墙特征：`0x177=22` 且 `0x183` 起跳。
- 窗口模式下失效的连续引擎专属功能/诊断：带内微抖 `0x17E-0x181`、`0x185/0x186`、
  `0x187 bit0/bit2`、`0x176`；`0x18C bit1/bit2` 恒 0（判读引擎要看 `0x187 & 2`）。
- **红线**：`stepper_driver.cpp` 的 CCR 预装载（:116）与 `TMR2->swevt_bit.ovfswtr`（:132）
  绝不能删——角度模式 tier3 会把 CCR 写成 1 tick，删掉后窗口装载每窗白送一个沿
  （= 20000 微步/秒）。

### 同一天顺带确认/修掉的其他事
- **修 B（`8cb1d1f`）**：`0x121` FE 的参考项取自"计划账"（∫规划速度 dt），而结束判据是
  "实发账"跑满命令；闭环下补偿只进实发账 ⇒ 两本账在停车瞬间恒差一个补偿积分，FE 看起来
  "只有落点误差的一半"（实测 −1.043° vs 真实 −2.1°）。修法：进 SETTLE 时把参考账对齐到
  命令行程；验证后 FE 与实测落点误差吻合到 0.06° 以内。**不是任何 2× 刻度因子**——
  `0x100` 现为 32、`spr=6400` 正确（老版 `c756ffa` 的 `0x100` 读回 64、`spr=12800`，
  它的 FE/位移显示是半标，且它的"半圈"按钮 `spr/2` 实际走一整圈）。
- **今天被证伪并放弃的方向（别再走）**：①"账本按时间积分所以多走"——把账本改成读 DMA
  计数反而更差（`4dea3b6`，已回滚，见 `4e1552d` 说明）；②"STEP 悬空/DIR 耦合"——改动
  引脚处理无改善（`3b39222`、`32b9672`，已回滚）；③"停后沉降漂移"——停 2 秒只再走
  −0.2~−1.0 微步；④"滞后角补偿"——`0x166=0`、`0x151=0` 本来就没开；⑤"整圈 vs 半圈的
  测量几何抵消"——不成立，`c756ffa` 跑 3200 也不累积。
- **磁编码器校准"第一圈转过 360°"问题：已修复（2026-11-17，用户实测确认）。**
  原症状：校准过程中第一圈累计角度会超过 360°（圈数/解绕在跨 0° 边界处多算一圈）。
  以后回归测试按 `0x144` 校准流程走一遍即可，不必再当已知缺陷记录。
- **待修 A：闭环停后不做任何修正**（详见 docs/findings_2026-11-17.md §6、§8）。
