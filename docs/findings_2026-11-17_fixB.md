验证修 B 通过：FE 现在等于真落点误差；并暴露"闭环比开环更差"的机理

实测（闭环 0x107=1，`scripts/tt_feref_tmp.py`，避开正好 180° 的 unwrap 边界）：

  命令 1600 步(90°)：落点误差 −1.275 / −1.121 / −1.831°   FE −1.268 / −1.120 / −1.774°
                     FE − 落点误差 = +0.007 / +0.001 / +0.057°
  命令 4800 步(270°)：真落点误差 −2.286 / −2.148 / −2.336°  FE −2.312 / −2.125 / −2.351°

⇒ 修前 FE 只有落点误差的一半（−1.043° vs −2.1°），修后两者吻合到 0.06° 以内。
⇒ 证实根因是"参考账取错本"（FE 参考用 ∫规划速度 dt 的计划账，运动结束判据却是实发账跑满
   motion_pulse_count_，闭环下补偿只进实发账），不是任何 2× 刻度因子。

脚本两处已知缺陷（不影响结论，下次修）：
  · 4800 行打印 −92.286° 与 "FE−落点 +359.97°"：脚本用 a0→末点单点差做 unwrap，跨 ±180°
    边界翻转；加 360° 后即 +267.714°，与 FE 一致。应改回逐拍积分或对已知行程做基准修正。
  · 0x190 FE_REF_STEPS 静态读回 0：stopMotion() 会清两本账，必须在运动中抓峰值才有效。

【新暴露的关键事实】闭环落点误差随行程增长，且比开环差一个量级：
  闭环 90° 少走 1.27°；闭环 270° 少走 2.29°（≈ 行程的 1.3%）
  开环同机同参数：整圈 6400 微步残差只有 +0.6~+1.8 微步（0.03~0.10°）
机理：总行程被账本封顶（motion_planner.cpp:354 发满 N 就结束），补偿只调制速度
  （motion_planner.cpp:898 `pps = current_step_speed_ + compensated_rps_*spr`），
  **位置环没有任何"多走一段"的手段**，于是整段积累的滞后角在停车瞬间原样留在轴上，
  而停后修正通道又因 motion_running_=false 直接 return（closed_loop_controller.cpp:1940-1944）。
  两条叠加 = 闭环落点比开环差、且与行程成正比。

结论：修 A（RAMP_STAGE_HOLD 停后补发同号"少走"）是对症的，且 −1.27°/−2.29° 都远超
0.45° 进入阈值，必定触发。补发量按 |FE|/0.05625° 折算，上限 2 次、总时长 500ms。
